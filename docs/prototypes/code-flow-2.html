Following a flow (v2): the route drawn on the tree

Try: press ▶ in Flows, then → / Space to walk it, Esc to stop. The numbered stops sit on the tree's edge, the route between them is drawn (solid where you've been, dashed ahead, with the hop named where it leaves the process), and the card says what the step does and where the next one goes. With follow on, only the folders the flow touches stay open. Click a row to see just its own calls. Same data as v1.

How deeper links (file to file, function to function) fit

  • One rule for every level. A line is drawn between the nearest rows that are showing, the same rule atlas uses for boxes. Closed folders gather their files' lines; open a file and its lines move to its functions. So "file uses file" and "function calls function" are the same lines at different depths.
  • Dependencies stay off until asked (the ⇄ icon): drawn inside the node's right gutter, so they never cross the flow or the library lines.
  • A flow is a path through function rows. Each step names a function; the line goes to the nearest showing row, so a flow still reads with everything collapsed (it points at folders) and gets precise as you open things.
  • Where the facts come from: files and libraries from the repo; functions and calls from an index (tree-sitter or the language server) when there is one, else what an agent drew. A flow is drawn by a person or an agent, and checked against the index: a step whose function is gone shows as broken.
  • Process hops (CLI → node over a socket, node → hub over HTTP) are the existing atlas connections between running boxes, shown between steps, so the code flow and the architecture agree.
