atlas: looks to pick from

Local prototypes only, nothing built. Each section has a few options, drawn with the real agent-comms boxes (board crates, Rust libraries, hub/node, the model server). The my pick tag is a starting point for us to argue about, not a decision.

1. Libraries without a fan of arrows

Today the board-bin view draws seven edges into one "Rust libraries" box. Other tools keep libraries off the arrow layer: one icon plus a "+N" chip (IcePanel), or a matrix (Structure101, Lattix).

A · chips on the box my pick

+ who uses what is on the box you're reading. − the label ("serves", "MCP") moves to hover.

B · "+N libs" that opens

+ cards stay quiet. − one click to see anything.

C · a "who uses what" matrix view

Its own kind of view, made from the same rules (rows: libraries, columns: what's on the view). + answers "what breaks if I drop reqwest". Goes well with A.

2. Code next to the running thing

Board hub (runtime) is built from crates/board/src/hub/. Nx groups folders into nodes that open in place; cargo-modules prints a tree. Structurizr and IcePanel have no code link, just a URL.

A · "built from" pill + tree panel my pick

crates/board/ bin ├─ main.rs clap planned ├─ hub/ ◀ Board hub axum, rmcp planned ├─ node/ ◀ Board node reqwest planned │ └─ adapters/ planned ├─ cli/ ◀ board CLI reqwest planned └─ store/ ◀ Board database rusqlite planned
Clicking the pill opens the crate as a tree in the panel, with the runtime boxes each folder builds. + no extra boxes on the canvas.

B · a crate as one card that lists its folders

A "folder card": rows instead of boxes, and a row opens like a box does. + eight boxes become one. − arrows land on rows, so it's a new kind of drawing.

C · two lanes: running | code

Dotted "built from" lines only show on hover. + reuses lanes we already have. − twice the boxes.

3. A build plan on the diagram

ArchiMate's idea: build steps are their own things that deliver boxes; the diagram shows how far along you are. LeanIX draws lifecycle phases; IcePanel freezes versions.

A · step numbers + a scrubber my pick

Show the board after step 1234all
#stepdeliversstate
1board-core typesenvelope.rs, address.rsdone
2store + hubstore/, hub/done
3CLIcli/, main.rsbuilding
4node + adaptersnode/planned
Step states here are made up to show the look.

B · the status alone says it

planned: dashed · building: striped · live: solid. No steps, no order. + nearly free (status exists). − no "what's next".

4. Runs N times, or once per host

Structurizr gives a deployment node instances: a number or a range (1..N, 0..1). UML writes multiplicity in a corner. Nobody I found draws "once per host" well.

A · stacked card + count

A shadow card behind it means "more than one". The corner says how many: ×3, 1..N, 0..1.

B · "per host": a ghost in every host frame my pick

Board node is set to "one per host boundary", so every host frame shows it; the copies are faint and open the same box. + uses the host boundaries we just added.

5. Optional parts and alternatives (slots)

Feature models (FeatureIDE): an empty circle is optional, an arc joins alternatives. The model server already reads like this: an embedder with alternatives, a router that's optional.

A · optional mark

An empty circle on the corner, "optional" in the footer. Router can be off; the board still works.

B · a slot with candidates my pick

The box is the role ("Embedder"); the candidates are chips, the chosen one filled. Arrows go to the role, so swapping doesn't touch them.

C · feature-model arc

Real alternatives as sibling boxes joined by an arc. − the notation isn't standard, people won't know it.

6. Profiles

Ilograph picks a "context" separately from the view. A profile here would pick which slot candidate, which optional parts, and how many of each, so the same diagram reads "laptop" or "desktop".

A · a profile switch over any view my pick

Profile alllaptopdesktop
Boxes outside the profile go faint but keep their place, so switching doesn't reshuffle. (On the laptop there's no model server: models live on the desktop.)

To talk through

  1. Libraries: chips on boxes (1A) plus a matrix view (1C), and drop the "Rust libraries" box and its arrows?
  2. Code: a path/"built from" on runtime boxes and a tree in the panel (2A), rather than code boxes on the canvas. Or do you want code views to stay real boxes like the s-chan agent drew?
  3. Build plan: are steps their own thing (3A), or is status enough for now (3B)?
  4. "Per host" (4B) means a box can point at a boundary kind. Is host the only one you need, or also region / project?
  5. Slots (5B) and profiles (6) are one feature really: a profile fills slots and sets counts. Build them together, or slots first?
